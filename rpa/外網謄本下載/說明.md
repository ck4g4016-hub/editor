# 外網謄本下載：把每一份謄本對回 Excel 的那一列

這個資料夾只放**對時的邏輯與它的測試**。流程檔本身（PAD 匯出的 .txt）
不放進來：這個 repo 是公開的，而流程檔的控制項庫裡有畫面截圖。
流程檔在承辦人那裡；要改的時候請他重傳一份。

## 為什麼要有這個

承辦人 2026-10-12 回報：「明明是照順序下載，但是裡面的內容跟標題不符，
但是我在查調網站內看到的順序是對的。」

原因是檔名用「順序」配：領件區第 N 個待下載的，就當成這一批第 N 個送出去的。
可是領件區列的是這個帳號**當天所有**的申請 —— 那天上面已經有一筆別的案子，
於是這一批每一份的檔名都錯開一份，冠到別人的謄本上，從檔名上完全看不出來。

（承辦人當時傳來的流程檔還是更早的版本：檔名用 `%LoopIndex%`，那是送件迴圈
的計數器，送完之後就不會再變，同一批每一份拿到同一個號碼。那也不對，一起換掉。）

## 現在的做法

* **送件時**：按下「送 出」之後，把電腦時間寫進 Excel 的 I 欄（`送件 yyyy-MM-dd HH:mm:ss`）。
* **下載時**：`find.js` 拿這一列的送件時間，去比領件區每一列的「申請日期時間」。
  * 先用一個 HEAD 請求問網站現在幾點（回應標頭的 `Date`），算出電腦跟網站差幾秒。
    只送給同一個網站，不帶任何資料。
  * 問不到的話改用「這一批全部的送件時間」推算差多少，而且這條路比較嚴：
    只要有另一種差很多的對法一樣合理，整批都不認。
  * 對不到、或同時對到兩筆 → 不下載，J 欄寫「未下載：原因」，最後列出來。**不猜。**
* `click.js` 點開之前再確認一次收件號沒變，再用**那一列的**文號＋身分證號命名。

為什麼一定要量網站時間、不能只靠推算：只靠推算的話，如果電腦時間剛好慢了
「一筆的送件間隔」，而領件區前面剛好有一筆別的案子，「整批錯開一份」跟
「完全對齊」看起來一樣合理 —— 推算會挑錯，錯的方式正好就是這次要修的那種。
`tests.py` 第 4、5 個情境就是這個陷阱。

## 欄位位置是怎麼確定的

領件區畫面上看得到的欄位：申請日期時間、資料來源、資料收件號、資料種類、
張數、狀態、下載日期時間、錯誤描述。原本的流程用 `cells[2]` 取資料來源、
用 `td:eq(7)` 判斷下載過沒有，兩者都用了好幾個月沒出錯，所以每一列最前面
有一欄看不到的。因此：申請日期時間 `cells[1]`、收件號 `cells[3]`、
下載日期時間 `cells[7]`。每一列都會驗格式，不對就整個停下來回報，不硬猜。

## 已知的限制

* 只看得到領件區**目前這一頁**。一批太多、分到下一頁的那幾筆會是「對不到」。
* 領件區預設只列**今天**的申請。改天才用「僅下載謄本」補抓的話，全部會是「對不到」。
* 用舊版流程送出去的件，Excel 沒有 I 欄，沒辦法對，流程會直接說明並停下來。
* 領件區裡別的案子**不會**被下載（以前會一起下載、一起壓進去）。

## 檔案

| 檔案 | 用途 |
| --- | --- |
| `find.js` | 在領件區找這一列送出去的那一筆 |
| `click.js` | 點開那一筆；點之前再核對一次收件號 |
| `build_flow_v1.py` | **現在用的這支。** 以 2026-09-24「照文號排序」那一版為底（保留之前所有修正），只換掉照順序配檔名那一段：`python3 -I build_flow_v1.py 照文號排序.txt 新的.txt` |
| `build_flow.py` | 以更早的 1017 版為底的同一個改法（承辦人 10/12 第一次傳的是那一版）。留著備查 |
| `verify_flow.py` | 檢查產出的流程：控制項庫沒被動到、每段 JavaScript 都能解析、嵌進去的跟測過的一模一樣、區塊有開有關 |
| `tests.py` | 在 Chromium 裡用仿造的領件區頁面跑 12 個情境（需要 playwright） |
| `harness.py`、`padjs.py` | 上面兩支用到的工具 |

改 `find.js`／`click.js` 之後，三支都要重跑，而且**要做負向驗證**：
故意把邏輯改回「照順序配」，`tests.py` 第 1 個情境一定要失敗。
